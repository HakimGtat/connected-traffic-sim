# Connected Traffic Simulator: Project Plan

**Idea:** Simulate traffic where cars talk to each other (V2V) and to traffic lights (V2I), and measure how much flow improves when we remove human reaction time. Latency is modeled realistically, so crashes caused by slow messages can happen.

**Decisions made**
- Goal: portfolio piece (public repo, clear before/after results, dashboard + demo video)
- Simulator: **SUMO** + Python (TraCI / libsumo). No CARLA.
- Messaging: simple Python latency/drop model, behind an interface so Veins/OMNeT++ can be swapped in later
- Light optimizer: rule-based first, reinforcement learning (sumo-rl) as a stretch goal
- Map: synthetic grid for development, then a real Ottawa corridor from OpenStreetMap for the showcase

---

## Prior art (so the write-up positions it honestly)
- **V2X / DSRC / C-V2X**: the real-world standards for car-to-car and car-to-infrastructure messaging.
- **CACC / platooning**: cooperative adaptive cruise control; cars share acceleration so followers react instantly.
- **SPaT + GLOSA**: lights broadcast their phase timing; cars adjust speed to arrive on green.
- **Tools**: SUMO, Veins, Artery, Eclipse MOSAIC, sumo-rl, RESCO, Flow.

**What's mine:** one experiment harness that compares human drivers, connected cars, and connected cars + smart lights side by side, with a **latency vs. safety tradeoff curve** (how much delay before crashes appear).

---

## Architecture

```
SUMO (roads, cars, lights)
   ↑↓  TraCI step loop (Python)
Orchestrator ── Scenario config (YAML): map, demand, % connected cars, latency, controller
   ├── Vehicle agents   → publish state (pos, speed, accel, brake flag), react to messages
   ├── Light agents     → publish SPaT (phase, time to change), receive approach info
   ├── MessageBus (interface)
   │     └── SimpleBus: delay (ms), jitter, drop %, range (m)   [later: VeinsBus]
   └── Metrics logger   → CSV/Parquet per run
Analysis + dashboard (pandas, Plotly/Streamlit or Power BI)
```

Key detail: SUMO's default car-following model avoids crashes. For latency to cause crashes, connected cars use a custom controller with SUMO's safety checks turned off (`speedMode`), and SUMO collision detection is turned on (`--collision.action warn`).

## Phases

### Phase 0: Setup (≈ 1 week)
- Install SUMO on Windows, Python venv, `traci`/`libsumo`, git repo.
- Run a sample scenario in `sumo-gui` and step it from Python.
- **Done when:** a Python script spawns cars on a grid and logs their speeds.

### Phase 1: Baseline traffic simulator (≈ 2 weeks)
- 3×3 grid network (`netgenerate`), traffic demand with `randomTrips` / `routeSampler`.
- "Human" drivers: Krauss/IDM model with reaction time (`tau`, `actionStepLength` ≈ 1 s) and start-up delay at green.
- Fixed-time traffic lights.
- Metrics: average travel time, delay, queue length, throughput per green, stops per car, CO2/fuel (SUMO built-in), collisions.
- **Done when:** repeatable baseline runs (fixed random seeds) produce a metrics table.

### Phase 2: Traffic light optimizer (≈ 2–3 weeks)
- Step 1: SUMO's actuated / delay-based lights as a cheap comparison point.
- Step 2: own rule-based controller (queue-length / max-pressure).
- Step 3: lights broadcast **SPaT**; connected cars get "green in X s" and start rolling with no reaction delay (the "green light hesitation" fix).
- **Done when:** a chart shows fixed-time vs. actuated vs. own controller on the same demand.

### Phase 3: Car-to-car communication (≈ 3 weeks)
- `MessageBus` interface + `SimpleBus` (latency, jitter, packet loss, range).
- Messages: periodic status beacon (~10 Hz) + event messages (hard brake).
- Connected car controller: CACC-style. Uses the leader's broadcast accel, a shorter time gap, instant brake propagation down the chain.
- **Penetration rate** knob: 0%, 25%, 50%, 100% connected (mixed traffic is the realistic case).
- Brake-wave test: lead car slams brakes; compare how the wave spreads with humans vs. connected cars.
- **Done when:** brake-wave and flow comparisons work at several latencies.

### Phase 4: Experiments + latency/safety study (≈ 2 weeks)
- Sweep: latency (0–500 ms) × drop rate × penetration × controller.
- Multiple seeds per config; report means and spread.
- Headline outputs:
  1. Travel time / throughput improvement vs. baseline
  2. Green-light start-up time lost (human vs. connected)
  3. **Latency vs. collisions curve**: the "safe latency" threshold
- **Done when:** results table + charts are generated by one command.

### Phase 5: Real map + showcase (≈ 2 weeks)
- Import an Ottawa corridor from OpenStreetMap (`osmWebWizard`, e.g., a stretch of Bank St or Rideau St).
- Rerun the key experiments on it.
- Dashboard (Streamlit or Power BI) + short `sumo-gui` screen recording of baseline vs. connected.
- README with method, limitations, and results labeled as **simulation results**.
- Add to portfolio (`src/content/projects/<slug>.mdx`, `npm run explain`).

### Stretch goals
- RL traffic lights with `sumo-rl` (PPO/DQN) vs. the rule-based controller.
- Swap `SimpleBus` for **Veins/OMNeT++** for realistic radio (WSL2/Linux recommended).
- Crash-mitigation strategies (your "solution later"): adaptive time gap based on measured latency, fallback to sensor-only mode on message loss.
- Emergency vehicle priority (lights + cars clear a path).

## Risks and mitigations
| Risk | Mitigation |
|---|---|
| SUMO's car models prevent crashes | Custom controller + `speedMode` + collision detection on |
| Python step loop slow with many cars | Use `libsumo` instead of TraCI socket; keep grid size modest |
| Results look too good / unrealistic | Mixed penetration rates, packet loss, multiple seeds, honest limitations section |
| Veins setup painful on Windows | Deferred to stretch; interface keeps the swap clean |

## Total estimate
About 12–14 weeks part-time for Phases 0–5; stretch goals after that.
